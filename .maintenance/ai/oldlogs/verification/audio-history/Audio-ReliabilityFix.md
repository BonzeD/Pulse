# ReliabilityFix — исправление совместимости аудио после AudioDiagnostics2

Текущая ветка: Pulse 1.0.3 + StartupFix + AudioDiagnostics2 + ReliabilityFix. Это не полный откат приложения на 1.0.2. Интерфейс, аккаунты, локальная библиотека и предыдущие несвязанные исправления сохранены.

## Основание

Сравнён пользовательский архив Pulse-1.0.2.zip, включая реальный offline.js и бинарные компоненты. В приложенном коде 1.0.2 есть fastResolve перед yt-dlp, хотя в пользовательской среде рабочим путём обычно оказывался yt-dlp. Стабильный proxyStream при отказе ссылки мог повторно получить URL и продолжить тот же запрос.

В версии AudioDiagnostics2 дополнительная проверка резервного URL могла сразу завершить resolve ошибкой при первом HTTP 403. Тогда renderer переходил к embed, который для некоторых видео запрещён (в новом пользовательском логе — код 150). При повторе того же трека новый URL уже мог открыться. Это воспроизведено локальным тестом: реальный исходник 1.0.2 восстанавливает запрос; предыдущий AudioDiagnostics2 возвращает 502; ReliabilityFix возвращает исходные аудиобайты.

## Изменения

1. **Один ограниченный повтор получения резервного URL при 401/403/410 до fallback.** Если первый URL yt-dlp отклонён, выполняется ещё одна extraction и проверка. Максимум две extraction на один backupResolve, не бесконечный цикл. Ошибки запуска, запрет видео, неподдерживаемый формат и отмена не запускают этот повтор. Явные ограничения самого YouTube не снимаются.
2. **Метаданные yt-dlp вместо голой строки URL.** Используется `--dump-single-json` с прежним выбором качества `bestaudio[ext=m4a]/bestaudio`. Для проверки и воспроизведения сохраняются заголовки выбранного потока: User-Agent, Referer, Origin, Accept-Language. Cookie, Authorization и произвольные заголовки из результата не переносятся. Cookies аккаунта для самого yt-dlp используются как прежде, без выхода из аккаунта или удаления пользовательских данных.
3. **Защита от ложноположительного быстрого результата.** Прямой путь принимает форматы с длиной файла и конечной длительностью, отбрасывает признаки live/DVR-фрагментов. Для HTTP 206 проверяется согласованность Content-Range / Content-Length / общего размера. HTML, пустое тело, противоречивые диапазоны и неподдерживаемый HLS/DASH-segmented extractor result не выдаются за обычный музыкальный файл. При неполных метаданных прямого клиента используется более медленный резервный путь, а не случайный фрагмент.
4. **Кэш ссылок переведён на verified:4.** Старые ссылки verified:3 не загружаются с диска. Это только повторное получение временных URL: библиотека, офлайн-файлы, cookies и аккаунты не удаляются. Новый кэш сохраняет только разрешённые media headers.
5. **Таймер старта отделён от ожидания resolve.** Старый 12-секундный media-watchdog мог увести трек в embed во время ещё работающего повторного получения ссылки. Теперь он не заменяет незавершённый backend resolve; отсчёт буферизации начинается заново при назначении audio.src. Тайм-аут самого процесса yt-dlp остаётся ограниченным. Пауза во время ожидания по-прежнему запрещает последующий autoplay; смена трека не позволяет старому ответу заменить новый.
6. **Копирование большого аудиолога исправлено.** Отдельная native-команда audioCopy копирует текущий ограниченный диагностический снимок прямо из main process. Общий dev:copy не расширялся: старый лимит и проверки доверенного окна сохранены. Системная ошибка clipboard возвращается как ошибка, не как успешное копирование.

Запись остаётся добровольной, анонимной и ограниченной по времени/размеру. В JSON добавлены безопасные причины invalid-range / unsupported-format / backup-retry / invalid-output. Заголовок: `diagnosticsVersion: 2`, `build: ReliabilityFix-AudioDiagnostics2`. Ни URL, ни значения заголовков, ни сырой JSON/stderr yt-dlp в диагностический экспорт не попадают.

## Что это не обещает

- Не все треки обязаны стартовать быстро. Сомнительный прямой поток больше не считается успехом: такой трек может ждать yt-dlp и, при отказе ссылки, один повтор.
- Не заявляется исправление любых ограничений YouTube: недоступные, удалённые, гео-/возрастные или запрещённые для embed видео могут оставаться недоступны.
- Поскольку сборка выполнялась под Linux, реальный запуск Windows portable и настоящие проблемные треки в пользовательской сети здесь не проверены. Нужен повторный пользовательский тест; приложение не подписано цифровой подписью.

## Проверки и сборка

Добавлены регрессионные сценарии: стабильный 1.0.2 как положительный контроль, прежний AudioDiagnostics2 как отрицательный контроль; повтор первого 403; постоянный 403 с ограниченным числом попыток; выбранные заголовки на probe и proxy; кэш старого/нового поколения; противоречивые диапазоны; DVR и неподдерживаемые форматы; HEAD; большой аудиолог через настоящий native IPC-обработчик с проверками доверенного окна; ожидающий resolver дольше media-watchdog и пауза при ожидании.

Исторические approved-манифесты не переписаны. Новый точный test-only inverse отделяет ReliabilityFix от предыдущей версии, а старые отрицательные контроли по-прежнему восстанавливают прежний код. Стабильный offline.js включён только в tests/fixtures и закреплён SHA-256, а не используется production-кодом.

Локальные Chromium-сценарии проверяют реальные HTTP-запросы к фикстурам, WAV-декодирование, AudioContext/analyser, конечную длительность, паузу и seek. Это не реальные замеры YouTube и не Windows-тест.

Только portable: из app выполнить `npm ci`, затем `npm run build:media` (.NET 8 + Windows targeting), затем `npx electron-builder --win portable --x64 --publish never`. Старый `npm run dist` также вызывает setup и не подходит для portable-only.

## Проверка пользователем

Закрыть предыдущую Pulse и запустить ReliabilityFix-portable. Проверить два ранее неработавших трека и один обычный. Если трек не открылся, дождаться окончательной ошибки, не переключая его слишком рано; сохранить или скопировать новый аудиолог. Убедиться, что build равен ReliabilityFix-AudioDiagnostics2. Для сравнения со стабильной 1.0.2 использовать тот же трек и те же условия входа/сети.
